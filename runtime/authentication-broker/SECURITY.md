# Security notes

The broker is intended for authorized, researcher-controlled bug bounty accounts. Its policy file does not create authorization. Missing or stale policy, worker identity, account, origin, method, technique, exact endpoint authorization, request limit, expiry, or egress protection must deny target traffic. Runtime target and attended-login origins must use HTTPS; automatic refresh origins are not currently supported and must be empty.

Application credentials remain in a broker-owned browser context and local profile. Never copy cookies, tokens, passwords, MFA values, profile files, or Playwright storage state into a prompt, policy, audit log, evidence artifact, or Git. Persistent profiles require verified OS volume encryption and current-user-only access; otherwise use an in-memory context and sign in again after restart.

Development and acceptance verification use loopback mock targets and synthetic accounts only. This package must not bypass MFA, CAPTCHA, legal prompts, rate limits, or program restrictions. User sign-in, MFA, CAPTCHA, and login confirmation remain attended actions. A policy-file change invalidates the current policy until restart; the broker never copies the synthetic example into runtime data.

## Egress fence

Target capabilities remain disabled until the managed browser uses the local proxy and `egressPreflight()` verifies the current Windows state. Missing PowerShell access, an incomplete ActiveStore read, a disabled firewall profile, a mismatched browser path, any conflicting rule for that executable, or any changed broker rule returns `unverified`.

The proxy binds only to `127.0.0.1:8766`. The broker's eight named outbound block rules for the exact Chromium executable block every other IPv4 and IPv6 destination, including private networks, and block UDP to loopback. TCP to `127.0.0.1:8766` is the sole network exception. The rule ranges avoid an overlapping block on that one endpoint; an allow rule cannot safely override an overlapping explicit block because Windows Firewall gives explicit block rules precedence. See [Microsoft's rule precedence documentation](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules).

Install and remove the fence only as explicit researcher actions from an elevated PowerShell window. Review the dry run first with a synthetic path:

```powershell
.\scripts\install-egress-fence.ps1 -ChromiumPath 'C:\Synthetic\chrome.exe' -WhatIf
```

For a real installation, pass the exact managed Chromium `.exe` path returned by the browser runtime. The script prompts before creating only its named rules and refuses to overwrite a same-named rule that differs. It does not change firewall defaults or unrelated rules. To reverse an installation, pass the same exact path to `remove-egress-fence.ps1`; it refuses to remove a rule that no longer matches the broker's expected state. Removal also supports `-WhatIf`.

The browser launch configuration uses the fixed proxy, Chromium's `<-loopback>` subtractive rule to prevent implicit localhost proxy bypass, and `--disable-quic`. During attended login, the proxy may reach exact policy-listed target origins so an OAuth/OIDC GET or HEAD callback can return to the application; the managed browser route still blocks target-origin writes in this phase. POST-based login callbacks such as SAML ACS are unsupported and fail closed. Chromium documents the special bypass behavior in its [proxy configuration guide](https://chromium.googlesource.com/chromium/src/+/main/net/docs/proxy.md). Do not add a proxy bypass list or PAC script. If the active firewall policy cannot be read completely, do not substitute assumptions or direct browser egress.

The proxy requires a broker-issued, per-session proxy capability, allows only exact canonical origins and authorized methods, resolves all DNS answers itself, rejects the whole set if any address is local or special-use, and connects to a validated numeric pin. It checks the capability again after DNS resolution and for outbound bytes on an HTTPS tunnel, so a blocked, expired, changed-policy, or unverified-egress capability cannot keep using an established tunnel. HTTP redirects are not followed by the proxy; each subsequent request is checked independently. HTTPS uses CONNECT without TLS decryption, preserving the browser's TLS hostname verification and SNI. Since CONNECT hides the HTTP method and path inside TLS, the managed page adapter must enforce read-only page requests before they reach the tunnel, and the API adapter must enforce endpoint/method authorization before sending requests. A CONNECT tunnel is not a substitute for those request guards.

Firewall state changes are never made by broker startup or tests. The package's local mock tests inject DNS and a test-only loopback connector; production worker inputs cannot configure that connector. Startup does not bind the MCP listener until the exact proxy listener and current ActiveStore/firewall preflight succeed. The broker rechecks that state every 30 seconds; the next capability or browser request fails closed as soon as the check fails. The file audit writer appends metadata only, retains no in-memory history in production, and stops dispatch at its fixed 10 MiB limit rather than rotating or overwriting evidence.

## Local control boundary

The MCP worker and separate researcher HTTP controls bind to IPv4 loopback only. Researcher routes require the exact `Host` and `Origin` for the selected loopback port, JSON content type, and explicit confirmation on login confirmation and session close. They are not an authentication boundary against another process running as the same Windows user. Do not expose the listener through a reverse proxy, port forward, LAN bind, or shared machine account. The worker tool registry has no grant, profile, cookie, storage-state, DevTools, shell, arbitrary HTTP, or report-submission tool.

The researcher must inspect the current program authorization before issuing a connection grant. A grant is bound to one server-mapped worker connection, account alias, policy revision, role, tool set, policy reference, technique, exact origins, and methods. API requests additionally require an exact policy endpoint identifier and canonical path. Each validator must use an independent account session; sharing a cookie across agents invalidates authorization testing.

The browser's page route only permits methods from the page capability and currently requires GET for mapping. API methods are installed in a separate proxy scope and do not broaden the page route. API redirect following is disabled; every hop must independently match the endpoint authorization and consume a separate network-budget slot. Every allowed target-origin browser exchange, including subresources and GET/HEAD login returns, also consumes the account-wide rate/concurrency/request budget. That budget persists across profile close/recreation within the running broker and current policy revision. Worker tool-call limits are enforced separately. Only one active worker connection may hold a grant for a given engagement/account. Caller-supplied credential or routing headers are forbidden. A timeout is an unknown outcome and is never automatically retried. A 401 pauses the session for attended re-login. A 403 or 429 pauses the session, revokes all capabilities for the affected engagement/account, and requires researcher review plus a fresh grant; `/researcher/confirm-authorization-review` only resumes the session after review and does not restore worker access by itself. Worker `revoke_capability` also revokes the shared engagement/account session and interrupts its work.
